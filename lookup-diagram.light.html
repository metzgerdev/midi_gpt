How a token id becomes a vector

The embedding table is a 65×128 matrix of learned numbers — one row per token in the vocabulary. A lookup does not compute anything: it returns row i unchanged. Real weights, read from the trained bass checkpoint.

1 · input
14
A token id. One integer, no magnitude — 14 is not "more" than 2.
2 · index
W[14]
Select row 14 of the table. This is the entire operation.
3 · output
128 floats
That row, as-is. It becomes tok_emb in the input sum.

Why this counts as a learned linear layer

A lookup is exactly a one-hot vector times the matrix. Verified against the checkpoint: W[14] and one_hot(14) @ W are bit-identical.

The multiply is skipped because 64 of the 65 products are zero — indexing gets the same answer for a fraction of the work. But the equivalence is what makes the table a weight matrix rather than a dictionary: it is trained by the same gradient descent as every other layer, and the "lookup" is an implementation detail.

Gradients are sparse

Only the rows actually indexed in a batch receive a gradient. Feed token 14 and row 14 moves; the other 64 rows are untouched by that step.

So a token that never appears in training keeps its initial random values forever. In a 65-token vocabulary every symbol shows up constantly, so this is harmless here — but it is the same mechanism that leaves cond_proj sitting at initialisation, never having entered the graph.
